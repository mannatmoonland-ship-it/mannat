1. Project Overview

Mannat Moon Construction is a Flask-based construction management application. Its active modules support trade and worker-category setup, date-based site reports, material and supplier records, labour payments, ledgers, construction drawings, and building cost summaries. Super Admins also have user-management and local backup/restore tools.

The stack is Python with Flask and Jinja templates, browser JavaScript ES modules with HTML and CSS, and Firebase/Firestore for application data. Playwright is used by the Google Photos link helper; Requests is used for HTTP fetching. jsPDF and its AutoTable plugin are loaded by pages that create ledger PDFs.

Google Drive boundary: The Drawings Library saves a user-provided Drive PDF URL and opens that URL in a new browser tab. The current code does not use a Google Drive API client.

2. Project Folder Structure

  • app.py - Flask application entry point, configuration loading, session authentication, application routes, Firestore user-store classes, and Google Photos helper routes.
  • snapshot_routes.py and snapshot_service.py - Super Admin backup, verification, restore, and project-switch routes, plus snapshot data operations.
  • requirements.txt - Python package requirements.
  • templates/ - Jinja-rendered pages: dashboard.html, index.html (Trade Builder), labour_payments.html, daily_reports.html, materials.html, drawings.html, ledger_prints.html, building_cost_summary.html, snapshots.html, login/account pages, and the two guide pages.
  • static/ - Page JavaScript modules, shared dialog and connection-monitor assets, stylesheets, and calculation/PDF helper modules.
  • tests/ - Python and JavaScript regression tests for routes, business logic, and UI behavior. Root-level test_settlement_logic.js and test_settlement_logic.mjs are settlement logic checks.
  • instance/ and backups/ - Local runtime configuration and backup data. Treat their contents as environment-specific data, not source material for documentation.
  • README.txt - Existing setup notes, including the Playwright Chromium installation step.
Credentials: Local environment files and service-account JSON files may contain secrets. Do not copy their contents into documentation, logs, source control, or support messages.

3. Application Architecture

Flask backend

app.py creates the Flask app, loads environment configuration, provides session and role checks, renders pages, and serves JSON routes. It defines FirebaseFirestoreStore and an in-memory store used only when explicitly configured for development/testing. snapshot_routes.py registers a Flask Blueprint for administrator backup workflows.

Templates and browser modules

Files in templates/ are rendered with Flask/Jinja. Most operational pages load a page-specific ES module from static/. JavaScript uses DOM events and page-specific state; there is no single-page-app framework.

Firebase and Firestore

The browser-facing modules request the active public web configuration from /api/firebase-web-config, await the Firebase Auth custom-token bridge for the current Flask session, and then use Firestore for permission-scoped reads. Firestore Rules validate the token's Flask session ID and authorization version against the server-owned user record. Flask/Admin SDK APIs handle mutations; Admin SDK access bypasses Firestore Rules and must retain its own permission checks.

Active browser modules refer to collections including trades, daily_records, drawings_categories, drawings, and the material categories, suppliers, purchases, and consumption collections. Field shapes are owned by the respective module code; review those modules before changing data behavior.

Google Photos and Drive

The /google-photos helper tries Requests first and then a pooled headless Playwright browser to find a shared image URL; results are cached in process memory. Daily Reports can store photo/video evidence links. Drawing PDFs are linked by URL and opened by the browser; no Drive API integration is present.

PDF output

Trade and labour ledger output uses static/ledger_pdf.js and the page-loaded jsPDF/AutoTable browser libraries. Daily Reports use the browser print dialog for print and Save as PDF.

4. Python Environment and Dependencies

The repository does not declare a pinned Python version in a packaging manifest. Use a currently supported CPython version compatible with the listed packages. The project has been exercised in a Python 3.9 environment, but its installed Google libraries warn that Python 3.9 is end-of-life; use a supported newer runtime for maintained deployments.

Windows development setup

  1. Open PowerShell in the repository root.
  2. Create and activate a virtual environment:
py -m venv .venv
.\.venv\Scripts\Activate.ps1
  1. Install the declared packages and the Chromium browser used by Playwright:
python -m pip install -r requirements.txt
python -m playwright install chromium
  1. Configure the required local environment and Firebase credentials without adding secrets to source control.
  2. Start the app:
python app.py

The development entry point prints a local address at http://127.0.0.1:5020. It also binds to 0.0.0.0:5020 for network access; expose that only on a trusted network and with appropriate production controls.

Declared dependencies

requirements.txt declares Flask 3.x, Flask-Mail, python-dotenv, Playwright, Requests, and firebase-admin 6.5 through versions below 8.0. Package versions are bounded as shown in that file; no separate Python version pin is provided.

Configuration names

app.py loads local environment values with python-dotenv. Configure values in the deployment environment or a private local environment file; never paste secret values into this page or commit them.

SECRET_KEY
Flask session signing key. Set a unique strong value for each deployment; do not rely on the source's development fallback.
FLASK_ENV
The app enables secure session cookies when this is set to production.
FIREBASE_PROJECT_ID
Project ID for the active Firebase project.
FIREBASE_SERVICE_ACCOUNT
Optional path to the Admin SDK service-account JSON. If not provided, the app also checks for Application Default Credentials and its local service-account discovery.
FIREBASE_WEB_CONFIG
Optional JSON object for the browser Firebase app. Its project ID must match FIREBASE_PROJECT_ID.
FIRESTORE_MODE and ALLOW_IN_MEMORY_FIRESTORE
Control the configured store mode and explicit in-memory development/test fallback. Do not use in-memory mode when persistent production data is required.
MAIL_SERVER, MAIL_PORT, MAIL_USE_TLS, MAIL_USERNAME, MAIL_PASSWORD, MAIL_DEFAULT_SENDER
Configure Flask-Mail for password reset and test email workflows. Keep mail credentials private.

Snapshot project switching writes active project details under instance/. Treat runtime files in that folder as deployment state; do not copy credential values into source control.

5. Flask Application and Routes

app.py is the entry point and registers snapshot_blueprint from snapshot_routes.py. @require_login protects signed-in pages; @require_role("super_admin") protects administration pages. Snapshot API routes also validate a session CSRF token.

Page routes

  • GET / - Dashboard.
  • GET /login, POST /login, POST /logout, and GET/POST /change-password - Session and password flows.
  • GET/POST /password-reset-request, GET/POST /reset-password/<user_id>, and POST /reset-password/<user_id>/validate - Password reset request and link validation/completion. /super-admin-recovery handles the separate Super Admin recovery flow.
  • GET /trade-builder - Renders index.html in Trade Builder mode.
  • GET /labour-payments - Renders labour_payments.html, which includes index.html in financial-only mode.
  • GET /daily-reports, /materials, /drawings, /ledger-prints, and /building-cost-summary - Render their respective module templates.
  • GET /user-guide - Signed-in user guide. GET /developer-guide - Super Admin-only developer guide.
  • GET /user-management and related user-management routes - Super Admin account and staff-type management.
  • GET /snapshots - Super Admin backup and restore page.
  • GET/POST /google-photos, GET /extract-google-photos-url, and GET /image - Shared-photo image helper routes.

JSON and support routes

  • GET /api/firebase-web-config - Returns the active public web configuration to signed-in browser modules.
  • GET /api/daily-records/dates, POST /api/daily-records, and PATCH /api/daily-records/<record_id> - Daily Reports calendar and record operations.
  • /api/snapshots/... - Snapshot history, create, verify, delete, restore preview/restore, folder, and project-switch operations in snapshot_routes.py.
  • GET /health - Basic health response. GET /favicon.ico - Static favicon.

6. Frontend Architecture

Templates and page entry points

  • templates/dashboard.html - Dashboard card grid and signed-in user controls.
  • templates/index.html with static/app.js - Trade Builder; also supplies the Labour Payments view through templates/labour_payments.html.
  • templates/daily_reports.html with static/daily_reports.js - Date-based site records and evidence.
  • templates/materials.html with static/materials.js - Categories, suppliers, stock, purchases, and consumption.
  • templates/drawings.html with static/drawings.js - Drawing categories and PDF links.
  • templates/ledger_prints.html with static/ledger_prints.js, and templates/building_cost_summary.html with static/building_cost_summary.js - Ledger and cost summary views.
  • templates/snapshots.html with static/snapshots.js - Super Admin snapshot workflow.

Shared and supporting modules

  • static/dialogs.js and static/dialogs.css provide shared alerts, prompts, confirmation, and success/error dialogs.
  • static/settlement_logic.mjs, static/contract_payment_summary.mjs, and static/payment_sort.mjs support payment calculations and ordering.
  • static/materials_logic.mjs and static/building_cost_summary_logic.mjs contain material and cost calculations.
  • static/ledger_pdf.js creates ledger PDFs. Page-specific CSS files provide styles; office_connection.js and office_connection.css are injected into successful HTML responses by an app.py response hook.

Communication paths

Jinja renders page markup and route links. The page's ES module attaches event handlers to that markup. Operational modules read permission-scoped Firestore data through the authenticated Firebase Web SDK and send mutations to permission-checked Flask JSON endpoints. Snapshot actions use authenticated JSON requests with the page's CSRF header. Google Photos helper routes use ordinary form or fetch requests. There is no shared frontend framework or common REST layer for every module.

7. Firebase and Firestore Integration

Server-side connection

app.py uses the Firebase Admin SDK through FirebaseFirestoreStore. get_user_store() supplies the account store and caches the Admin client for the active project. Credentials are resolved from the configured service-account path or Application Default Credentials; the app also supports an explicitly selected in-memory store for development and tests.

The active project configuration is assembled by get_active_firebase_config(). It reads the project ID and optional web configuration from the environment, or the active project file managed under instance/. The Admin and browser project IDs must match.

Browser-side connection

Active Firestore-reading page modules import static/firebase_auth.js and await firebaseAuthReady before using the Firebase Web SDK. The bridge requests a custom token from Flask, whose identity and permission claims are compiled from the current authenticated account. The configuration endpoint returns only the public web-app configuration; never put Admin credentials in browser code.

Flask and browser data paths

  • Active browser modules use the Web SDK for the reads listed in firestore.rules. Direct browser writes are denied; trade, payment, contract, Materials, Drawings, Owner Scope, and Daily Reports mutations use permission-checked Flask APIs.
  • Daily Reports use Flask JSON endpoints for record dates, authors, safe trade/category-name options, creation, editing, and deletion. Daily records remain permission-scoped Web SDK reads. The trade-options endpoint omits embedded wage, contract, and payment fields.
  • Snapshot operations use authenticated Flask JSON routes in snapshot_routes.py; the page includes a session CSRF value with its requests.
  • Rules deny access by default, require an active Flask-backed Firebase session and permission claim for browser reads, and deny direct client writes. Emulator tests are in tests/firestore.rules.test.mjs; deploy the rules to every Firebase project the application can select.
  • Owner Scope data has no per-owner or per-user field. Its active read/write APIs are server-mediated; Building Cost Summary has permission-scoped read access only to the fixed owner-scope payments path. This is not per-owner isolation.

8. Database Collections and Document Structures

The names below are the collections directly referenced by the current source. Fields listed are important fields seen in the active reads and writes; optional and older records may contain additional fields.

Accounts and administration

users
Username, names, email addresses, role, custom staff type, and password hash are strings; status is a string, is_active and must_change_password are booleans, and active_sessions and permissions are string arrays. Reset/recovery hashes and expiry/status fields support recovery; plaintext passwords and reset tokens are not stored.
custom_staff_types
Custom role-name documents with string fields id, name, and created_by, plus ISO date-time strings created_at and, after edits, updated_at.
audit_log
Audit entries with string fields actor_id, target_user_id, action, details, and timestamp. The document ID is generated separately from the entry payload.

Trades, reports, and payments

trades
One document per trade. name is a string; workerCategories, commonFields, contractItems, and paymentTransactions are arrays. Trade timestamps are ISO date-time strings. A worker category is an object with string id/name/payment_type and date strings; daily-wage categories have numeric currentWage and a wageHistory array of objects with numeric dailyWage and date/time strings. Lump-sum categories have numeric lump_sum_amount and optional string work_description.
trades.contractItems[]
Nested under a trade, not a separate collection. Each object has string id/name, numeric amount, and ISO date-time strings createdAt/updatedAt.
trades.paymentTransactions[]
Also nested under the trade document, not a separate collection. Entries use string id, type, date, paymentMode, and remarks; numeric amount, labourEarned, advanceAdjustment, and outstandingBalance; and ISO date-time strings createdAt/updatedAt. Lump-sum entries may include string workerCategoryId and workerCategoryName.
daily_records
One site record per document. Dates, location/activity, trade ID/name, weather descriptions, materials, and notes are strings. workerCounts is an object mapping category names to numeric counts; totals and legacy worker-count fields are numbers. evidence is an array of objects with string type, title, and url. The server adds creator identity, ISO date-time strings, and edit attribution fields.

Materials and drawings

material_categories
Category name, unit, and description are strings; brands is an array of objects with string id/name. Create/update times use Firestore server timestamps.
suppliers
Supplier names, contact/address data, and phone/email fields are strings. categoryIds is a string array; categoryBrandAssignments is an array of objects containing a string categoryId and string-array brandIds.
material_purchases
date, category/brand/supplier IDs and display names, unit, and billLink are strings. quantity, rate, and totalAmount are numeric when applicable; non-Cement purchase quantity/rate may be null. Create/update times use Firestore server timestamps.
material_consumptions
date, category ID/name, unit, workLocation, and remarks are strings; quantity is numeric. Timestamps use Firestore server timestamps. The current UI records consumption only for Cement categories.
drawings_categories
String name, numeric sortOrder, and Firestore server timestamps.
drawings
Category IDs/names, drawing name, number, revision, Drive URL, and description are strings; sortOrder is numeric. Create/update times use Firestore server timestamps.

Relationships and shared collections

  • trades is shared by Trade Builder, Daily Reports (trade selection and worker categories), Labour Payments, Ledger Prints, and Building Cost Summary. Payment and contract records stay nested within each trade.
  • daily_records.tradeId identifies the selected trade; tradeName is also stored with the record. workerCounts records counts by category; there is no separate worker attendance collection in the active modules.
  • Material purchase and consumption documents refer to categories with categoryId and retain categoryName for display. Supplier assignments refer to category and brand IDs; purchases may also refer to a supplier by ID.
  • Current Material Builder code writes brand entries inside material_categories.brands. It also reads materials and material_brands when loading legacy data; this UI does not write those two collections.
  • Drawing documents refer to their category through categoryId; the category name is also copied to categoryName. Category sorting updates drawings_categories.sortOrder; drawing sorting updates drawings.sortOrder within a category.
  • Building Cost Summary reads material_categories, material_purchases, and trades; it shares the source collections rather than maintaining its own copy.
The IDs above are application-level document IDs or fields used to connect related records. Firestore does not enforce relational foreign keys for these values.

9. Authentication and Authorization

Login and session lifecycle

  • POST /login loads a user by normalized username and checks the submitted password with Werkzeug's check_password_hash. New and changed passwords are stored with generate_password_hash; plaintext passwords are not saved.
  • set_session_for_user() clears any old session, creates a new random session ID, and stores the user ID, role, and session ID in Flask's signed session. It also adds that session ID to the account's active_sessions list.
  • get_current_user() reloads the account and accepts the session only if its ID is still active. The session lifetime is eight hours; cookie settings are HttpOnly and SameSite=Lax, and Secure is enabled when FLASK_ENV is production.
  • POST /logout removes the current ID from active_sessions and clears the Flask session.

Roles and route checks

Built-in roles are super_admin, office_staff, and supervisor. Additional staff-type names can be configured. @require_login checks for a valid signed-in session; @require_role(...) checks a role. User Management, Snapshot, and Developer Guide routes are restricted to Super Admins. The ROLE_PERMISSIONS constants describe role capability labels, but individual Flask decorators remain the route-level checks.

The permissions list contains a labour_muster label, but there is no distinct attendance page or route in the active route/template set. Do not treat that label as an implemented muster workflow.

Password change and recovery

  • POST /change-password verifies the current password, checks that confirmation matches, enforces the configured minimum length and character classes, then saves a new Werkzeug password hash. On a password change, other active sessions are invalidated.
  • /password-reset-request issues a one-time reset link by email for an eligible active account with a saved email address. The stored token is hashed, expires after 30 minutes, and reset requests are rate-limited by account and IP.
  • Super Admins can reset regular staff accounts and set must_change_password so the user is asked to change their password at the next login. The Super Admin account uses the separate recovery flow. Reset tokens, recovery codes, passwords, and credentials must never be logged or included in documentation.
Flask route protection and the browser UI do not replace Firestore Security Rules. Because several modules access Firestore directly from the browser, configure the Firebase project's rules to restrict data access appropriately.

10. Daily Reports Architecture

Data model and trade relationship

The supported editable payload is defined by DAILY_RECORD_EDITABLE_FIELDS in app.py. It includes the date, floor/location, activity, trade ID/name, worker counts and totals, weather, materials, notes, and evidence. The server adds creator identity and timestamps; edits add last-editor attribution. The corresponding Firestore collection is daily_records.

static/daily_reports.js reads trades to populate the trade selector and load that trade's worker categories. It saves category counts in workerCounts and keeps legacy count fields such as masonCount, manMazdoorCount, and womanMazdoorCount in the payload. Reports refer to the trade by tradeId and also store tradeName.

Read and write paths

  • Records for the selected date are queried from daily_records in the browser module. Calendar date availability is fetched from GET /api/daily-records/dates?start=...&end=....
  • New records use POST /api/daily-records; edits use PATCH /api/daily-records/<record_id>. Both require a signed-in user and accept only fields in the server allow-list.
  • Deletion uses DELETE /api/daily-records/<record_id> after the in-page confirmation dialog. Flask requires an authenticated session, CSRF token, and the compiled daily_reports.delete permission, then deletes only that document from daily_records.

Visual evidence and output

evidence is an array on each daily record. The editor builds entries with type, title, and url; available types in the form are Photo, Video, Document, and Drawing. Links may point to YouTube, Google Drive, or Google Photos. Photo previews use direct image links or the Google Photos helper when possible; the saved evidence remains the link information.

Daily Reports print and export use the browser print dialog. Export PDF does not call a server PDF API: the user selects Save as PDF from the browser's print options.

11. Materials Module

static/materials.js defines the collection constants and reads these six collections when loading the module:

  • material_categories - Current category fields include name, unit, embedded brands (id and name), description, and timestamps.
  • suppliers - Contact fields, categoryIds, and categoryBrandAssignments connect suppliers to categories and brand IDs.
  • material_purchases - Purchase date, category ID/name, optional brand and supplier IDs/names, quantity, unit, rate, total amount, bill link, and timestamps.
  • material_consumptions - Date, category ID/name, quantity, unit, work location, remarks, and timestamps.
  • materials and material_brands - Read during module loading to include older catalog/brand data. Current Material Builder writes category brands inside material_categories.brands, rather than writing these two collections.

Material categories, materials, brands, and suppliers remain managed by the browser Web SDK. Operational purchase and consumption mutations use authenticated Flask endpoints under /api/material-transactions/, with session CSRF checks and compiled materials.transactions.write or materials.transactions.delete permissions. The Admin SDK writes only the intended record; consumption writes also validate available Cement stock transactionally. For Cement purchases, the server verifies quantity, rate, and calculated total. Other purchase categories use the entered amount. Building Cost Summary continues to read material_categories and material_purchases; it does not create parallel copies.

12. Trades and Labour Modules

Trade Builder

static/app.js stores Trade Builder data in trades. A trade document has a name, nested workerCategories, a commonFields list, nested contractItems, nested paymentTransactions, and timestamps. Saving a trade preserves its existing contracts and transactions while updating trade and worker data.

Worker category entries have an ID, name, payment type, and effective date. Daily-wage entries use currentWage and a wageHistory array; a history item contains dailyWage, effectiveFrom, and recordedAt. Lump-sum entries use lump_sum_amount, an effective date, and optional work_description.

Labour Payments and contracts

templates/labour_payments.html sets financial_only and includes templates/index.html. It is another view over trades, not another database collection. Contract items are stored at trades.contractItems[] with id, name, amount, and timestamps.

Payment entries are stored at trades.paymentTransactions[]. Current transaction types include mobilization advance, labour advance, labour settlement, and lump-sum payment. Shared fields include type, date, amount, labourEarned, advanceAdjustment, outstandingBalance, paymentMode, remarks, and timestamps. Lump-sum payments also record workerCategoryId and workerCategoryName. Labour Payment create, edit, and delete mutations use authenticated Flask APIs at /api/labour-payments/<trade_id>/transactions; the server validates permissions and updates the embedded array transactionally without changing the trade schema. Contract item create, edit, delete, and ledger-editor replacement use authenticated APIs under /api/trades/<trade_id>/contract-items and update only that field. Browser Firestore reads remain in place. The settlement and contract summary helpers are settlement_logic.mjs and contract_payment_summary.mjs.

Daily Reports also read the same trades documents for trade selection and worker categories. Ledger Prints and Building Cost Summary also read trade/payment data. There is no separate payment or contract collection in the active code.

A dedicated named-worker attendance/muster register is not implemented in the active pages, even though a labour_muster permission label exists.

13. Drawings Library

static/drawings.js uses two collections: drawings_categories and drawings. Category documents contain name, sortOrder, and timestamps. Drawing documents contain categoryId, copied categoryName, drawingName, optional drawingNumber, revision, description, required googleDriveUrl, sortOrder, and timestamps.

  • Create: category creation adds one category document. Adding a drawing adds one drawing document with its category ID/name and next order.
  • Edit: category rename updates the category and its drawings' copied category name in a batch. Drawing edit updates its fields; moving it to another category assigns the next order in that category.
  • Delete: the UI blocks category deletion while drawings reference it. Drawing deletion removes its drawing document but leaves the PDF file untouched.
  • Open PDF: the UI validates Drive/Docs hostnames and opens the stored URL in a new tab. It does not upload files or call Drive APIs.
  • Sort: moving a category batches sortOrder updates for category documents only. Moving a drawing batches order values for drawings in its current category only. The UI disables concurrent moves and restores the displayed order if a save fails.

The category relationship is the drawing's categoryId; categoryName is a display copy updated on category rename. There are no separate collections for drawing sorting history.

14. Google Drive Integration

Drive PDF links

The Drawings Library stores the user-entered googleDriveUrl string with each drawing. static/drawings.js accepts HTTP(S) URLs on drive.google.com or docs.google.com, then renders an Open PDF link targeting a new browser tab. The app does not upload PDFs, call a Drive API, or authenticate users to Google Drive. Access is governed by Google Drive's sharing settings and the viewer's Google session.

Daily Report evidence and previews

Daily Report evidence stores a type, title, and URL. Photo evidence can be a direct image URL, a supported Drive file link, or a Google Photos share link. The page builds direct image/Drive previews where possible. Video evidence can embed a YouTube thumbnail and use a youtube-nocookie.com player after play; other video links are offered as external links rather than being transcoded or hosted by this app.

The separate /google-photos helper and /extract-google-photos-url route try Requests and then a pooled headless Playwright browser to find an image URL from a shared Photos page. The helper caches extracted URLs in process memory. It does not use Google OAuth or bypass Google sign-in or sharing restrictions. /image fetches an image URL for display; this is image fetching, not an authenticated Drive integration.

15. PDF Generation and Printing

Daily Reports

Print Daily Page and Export PDF use the browser print workflow. static/daily_reports.css contains an @media print layout that hides controls and formats the selected report for paper. Export opens the print dialog; the user chooses the browser's Save as PDF destination. No server-side PDF rendering service is used for this workflow.

Trade and payment ledgers

The Trade Builder/Labour Payments page loads jsPDF and jsPDF-AutoTable from CDN script tags in templates/index.html. static/app.js builds trade and payment ledger PDFs in the browser. static/ledger_pdf.js also exports ledger content with jsPDF-AutoTable; templates/ledger_prints.html loads the same browser libraries for static/ledger_prints.js.

Generated ledger files use client-side doc.save(). If the PDF libraries are blocked or fail to load, check the browser Network panel and the configured network policy for the CDN hosts. The app does not provide a server-side PDF fallback.

18. Railway Deployment

Not Yet Configured: No Railway manifest, Procfile, Dockerfile, or production WSGI server configuration is present in this repository. A Railway startup command has not been verified.

python app.py is the development entry point and starts Flask's built-in server on port 5020. Do not assume it is a production-ready Railway start command. Before deployment, choose and test a production WSGI serving arrangement and platform port binding; do not copy an unverified command into Railway settings.

Configuration and Firebase

  • Configure the environment names listed in section 16 through the deployment's protected variable/secret settings. Never commit service-account JSON or environment secret values.
  • Provide network access and valid Admin credentials for the selected Firebase project. Ensure FIREBASE_PROJECT_ID and the Web configuration's projectId match.
  • Review Firestore Security Rules for browser-side Web SDK operations; there are no Firestore rules in this repository.

Persistent storage

Snapshot ZIP files and audit/history JSONL files are written under <app root>/backups/. Active project state and restored-project descriptors are under Flask's instance/ directory; temporary restore credentials are under the operating system's local application-data directory. The repository contains no Railway volume or mount configuration, so durability of these files on a hosted instance is not established. Configure and test persistent storage for the required paths or use an external backup process before relying on hosted snapshots.

Because no Railway service is configured here, deployment logs, health checks, restart behavior, outbound networking, persistent-volume mounts, and scaling have not been verified. Run a staging deployment and test sign-in, Firestore reads/writes, reset email, snapshots, and Playwright-dependent photo extraction before production use.

19. Security Considerations

  • Authentication: Passwords are hashed with Werkzeug helpers. Flask sessions use HttpOnly and SameSite=Lax cookies, an eight-hour lifetime, and the Secure flag when the source sees FLASK_ENV=production. Set a unique production SECRET_KEY.
  • Authorization: Page routes use @require_login; administration pages and snapshot operations require Super Admin access. Review decorators when adding routes. Client-side visibility is not authorization.
  • Firebase credentials: Keep Admin service-account files and mail credentials outside source control. The Admin credential is server-side only; the Web config endpoint returns the browser configuration, not the service account.
  • Firestore access: Browser modules perform direct Web SDK operations. Configure restrictive Firestore Security Rules in Firebase and test them independently of Flask role checks.
  • Sessions and recovery: Reset tokens are stored hashed, expire after 30 minutes, and reset requests have account/IP rate limits. Do not log or share reset fragments, recovery codes, cookies, or credential values.
  • Drive links: The app does not mediate Drive permissions. Share each PDF only with the intended audience; possession of a link does not replace Google Drive's access controls.
  • Snapshots: Snapshot routes require Super Admin access and CSRF validation. Local backup files may contain sensitive business data; protect filesystem access, retain backups intentionally, and test recovery before destructive restores.
  • User data: Use least-privilege access, avoid copying real user or project data into test environments, and remove test exports and temporary credentials when no longer needed.

20. Troubleshooting and Debugging

Flask does not start
Check that the virtual environment is active and requirements.txt is installed. Install Playwright Chromium if initialization or Google Photos extraction reports a missing browser. If port 5020 is occupied, identify the process before choosing a different local port; the printed URL and deployment configuration must agree.
Firebase connection or permission failure
Check the active project ID, Admin credential source, matching Web config project ID, and network access. For browser reads/writes, inspect the Firebase project's Firestore Rules. The UI's role checks do not grant Firestore access by themselves.
Login or page access problem
Confirm the account is active and that the requested route is allowed for its role. Admin and Developer Guide pages require Super Admin. Verify the stable SECRET_KEY and that an active user session remains valid; changing passwords intentionally invalidates other active sessions.
Photo or video preview problem
Check the source URL and its sharing permissions. The Google Photos helper supports accessible shared pages only and may need Playwright Chromium. YouTube embeds and remote images also depend on browser network policy and third-party availability; use the original link when a preview cannot load.
PDF or print problem
For Daily Reports, use the browser print dialog and choose Save as PDF. For ledger PDFs, check the browser Console and Network panel for blocked jsPDF or AutoTable CDN scripts, then retry with the ledger page loaded successfully.
JavaScript error
Open browser developer tools and inspect Console and Network requests for the failing page module. Check the Flask terminal for request errors. The front end also writes diagnostic messages with console.error; do not copy secrets or sensitive record contents into shared reports.
Where to inspect server logs
During local development, inspect the terminal running python app.py; Python uses app.logger and the Google Photos helper also emits standard output messages. A future hosted service's log location depends on its deployment configuration, which is not included or verified here.

21. Guidelines for Future Development

  1. Inspect the route, template, JavaScript module, shared helpers, and tests that own the behavior before changing it.
  2. Preserve existing module behavior and collection relationships. In particular, payments and contracts are arrays in shared trades documents, not independent collections.
  3. Follow the current Flask/Jinja page architecture and page-specific JavaScript modules. Reuse shared dialogs and calculation helpers where appropriate; avoid introducing an unneeded frontend framework.
  4. Keep credentials and real user/project data out of source, tests, screenshots, logs, and documentation. Review Firebase Security Rules whenever a browser-side collection read or write is added.
  5. Add or update focused regression tests for changed behavior, then run the relevant Python and JavaScript checks before deployment.
  6. Verify role access, mobile layout, printing, and external-service dependencies affected by a change.
  7. Update this guide and the User Help Guide when verified routes, fields, setup steps, or user-visible workflows change. Label planned features clearly until implemented.
